# hcs27_checkpoint_v0 conformance vector

A Vaara audit trail committed as an HCS-27 Transparency Log Checkpoint, with
the proofs a stranger needs to check it. Conformance is anchored to the bytes,
so any reader can recompute it without running Vaara.

## What it is

Seven hash-chained audit records, projected into HCS-27 log entries, committed
as an RFC 9162 Merkle root, and published in two checkpoint messages: one at
four records and one at seven, linked by `prev`.

| File | What it holds |
|---|---|
| `records.json` | seven chained `AuditRecord` values with their stored hashes |
| `entries.json` | the HCS-27 leaf entries, one per record |
| `checkpoints.json` | the two topic messages, `previous` and `current` |
| `proofs.json` | seven inclusion proofs and one consistency proof, 4 to 7 |
| `expected.json` | the roots, the chain head, and the seven verdicts |

Seven is deliberate. It is not a power of two, so the tree is lopsided and the
two ways of building it diverge in shape while agreeing on the root.

## How to check it without Vaara

```
python tests/vectors/hcs27_checkpoint_v0/_check_independent.py
```

The checker imports the standard library and `rfc8785` for JCS. It imports no
Vaara code, and it builds every primitive the opposite way round from the way
Vaara builds it: the Merkle root by recursive top-down split where Vaara folds
bottom-up, the inclusion proof by the RFC 9162 bit walk, the record hash
re-implemented from the documented field list. Producer and checker share no
code and no method.

Exit 0 means all seven verdicts matched `expected.json`:

- `chainRecomputes`, each record hashes to its stored hash and links to the one
  before it
- `entriesBindToRecords`, every entry carries the record hash at its position
- `rootRecomputes` and `prevRootRecomputes`, both published roots recompute
- `allInclusionProofsVerify`, all seven recompute the root
- `consistencyProofVerifies`, the four record tree is a prefix of the seven
- `checkpointShapeConforms`, the messages satisfy HCS-27's structural rules

Regenerate with `python tests/vectors/hcs27_checkpoint_v0/_generate.py`. Record
ids and timestamps are fixed literals, so the output is byte identical and any
diff is a real change.

## Agreement with the upstream implementation

The vector was verified against `standards-sdk/src/hcs-27/merkle.ts` and
`types.ts` from the Hashgraph Online standards SDK, run directly under
`node --experimental-strip-types`:

- Merkle roots agree for every tree size 0 to 64, and at 100, 127, 128, 129,
  200, 255, 256, 257, 341, 500, 511, 512, 513, 1000, 1023, 1024 and 1025.
  No mismatches.
- 110 inclusion and consistency proofs generated by Vaara verify in the
  upstream `verifyInclusionProof` and `verifyConsistencyProof`.
- Both checkpoint messages and all eight proofs pass the upstream zod schemas
  unmodified.
- Canonical JSON agrees on ASCII, on non-ASCII including Finnish umlauts, and
  on nested empty objects and arrays.

Vaara builds the tree bottom up, promoting an unpaired node. HCS-27 splits at
the largest power of two below n and recurses. The two constructions are
equivalent.

## Rules the bytes depend on

### Canonicalisation is JCS

The HCS-27 leaf preimage is `sha256(jcs(entry))`. Python reproduces JCS with
`sort_keys=True, ensure_ascii=False, separators=(",", ":")`. The default
`ensure_ascii=True` escapes every umlaut to `\uXXXX` and yields a leaf hash no
other implementation reproduces. The vector carries a Finnish umlaut in
`agentId`, so a regression breaks this test first.

The Vaara chain digest uses a different canonicalisation, keeping the
`ensure_ascii=True` default so that every trail already written stays
verifiable. The chain digest and the checkpoint leaf are separate functions
over separate inputs, and the checker exercises both.

### Base64 appears in two alphabets

Checkpoint roots are unpadded base64url in `rootHashB64u`. Proof path nodes and
proof roots are padded standard base64. HCS-27 uses both. A proof built with
the wrong alphabet fails without a useful error.

## What the entry carries

An entry holds identity and `recordHash`: record id, action id, event type,
timestamp, agent id, tool name, previous hash, chain version and tenant id.

It leaves out `data` and `regulatory_articles`. Both stay committed through
`recordHash`, so anyone holding the record can still prove what was in it,
while the public topic carries neither the payload nor Vaara's compliance
attribution, and caller shaped values stay out of the canonicalisation path.

`timestamp` is carried as a string and is descriptive only. `recordHash` binds
the time, because the chain digest hashes the float itself.

## Known limitations

- `metadata.type` is typed as the literal `ans-checkpoint-v1` in the upstream
  schema, so that is the only value a stock HCS-27 validator accepts. The
  standard delegates log entry schemas to consuming profiles but gives a second
  profile no way to name itself in that field. Vaara emits the accepted literal
  and carries its own identity in `stream.registry`, in the declared
  `log.leaf` formula, and in a passthrough `vaaraProfile` key.
- HCS-1 overflow inscription is not implemented. A Vaara checkpoint is a fixed
  handful of short fields and measures 461 bytes against Hedera's 1024 byte
  cap, so the builder raises an error if one ever reaches the limit.
- The checkpoint commits to the log. It says nothing about whether any record
  inside it describes a permitted act. HCS-27 does not define log entry
  schemas. This vector supplies one.
